# Blackhole Protocol

## Encryption Layer

The encrypted stream uses pure XChaCha20. Stream keys are derived from the per-epoch user secret with PBKDF2-HMAC-SHA256 using 32 iterations and a 32-byte output.

`key` is the global server key. It is used for obfuscation-header pool generation and first-packet header auth. For each connection, `userSecret = uint64be(v) || password`; this per-epoch user secret is used for the 8-byte user nonce auth tag, XChaCha20 encryption/decryption, and mux MAC.

### Nonce Setup

Nonces are not sent when the TCP connection is created.

- The client first packet carries a 24-byte XChaCha20 nonce.
- The client-to-server nonce is `16B random + 8B user auth tag`.
- The server-to-client nonce is derived from the authenticated client nonce and decrypted timestamp payload: copy the 24-byte client nonce, then XOR its last 8 bytes with the 8-byte UTC millisecond timestamp field.
- The user auth tag is `HMAC-SHA256(PBKDF2-HMAC-SHA256(name + "\n" + userSecret, "auth:", 32, 32), nonce[0:16])[:8]`.
- The server enumerates users and verifies the 8-byte user auth tag.
- The server does not send a nonce; server-to-client packets use the normal later-packet structure from the first write.

### Encryption Direction

| Role | Send encryption | Receive decryption |
|:---:|:---:|:---:|
| Client | Client nonce | Server nonce |
| Server | Server nonce | Client nonce |

## Obfuscation Header

Every mux packet has a plaintext obfuscation prefix outside the XChaCha20 encrypted stream. The mux header and payload are encrypted; padding and the packet MAC are plaintext:

```text
Client first packet to server:
  [32B plaintext obfuscation head] [8B header auth] [24B XChaCha20 nonce] [encrypted timestamp header+payload] [plaintext timestamp padding] [4B packet MAC] [6B plaintext obfuscation header] [encrypted first header+payload] [plaintext first padding] [4B packet MAC]

Server first packet to client:
  [6B plaintext obfuscation header] [encrypted mux header+payload] [plaintext padding] [4B packet MAC]
```

The obfuscation prefix, padding, and packet MAC are not encrypted. The client first packet's 32-byte head is covered by an 8-byte HMAC, and every packet MAC covers the plaintext obfuscation prefix, encrypted mux header/payload, and plaintext padding, so tampering is detectable.

### Key Derivation and Pool Generation

Each connection has a deterministic obfuscation-header pool generated by PCG32:

```text
k || k2 = PBKDF2-HMAC-SHA256(key, Salt, 1024, 16), split as two big-endian uint64 values
epoch = (uint64(utcSec) + k) / 86400 / 16  integer division
v = SHA256(uint64be(epoch))[:8] ^ k2
```

- `Salt = "2.5:"`; protocol salt is derived from `version.Version` using only `major.minor`, so patch-version changes do not change the protocol and major/minor changes cannot silently retain the previous key-derivation domain.
- On the client, each configured server gets a runtime-only random `utc_offset` in `[0, 86400*4]` seconds at startup, and client-side pool generation uses `utcSec - utc_offset`.
- The hash step hides the low-entropy shape of the 16-day epoch before `k2` is mixed into the PCG32 seed.
- `v` is used as the HMAC key for first-packet header auth.
- `v` is the PCG32 seed used to generate the obfuscation-header pool.
- The pool rotates every 16 days.

### Pool Structure

`GeneratePool(v)` deterministically creates:

| Field | Description | Range |
|:---:|:---|:---:|
| Handshake magic | First-packet magic bytes, effective length `Len` | `Len ∈ {3,4,5,6,7,8}` |
| N | Total number of data headers | `[16,80)` |
| Threshold | Small/large packet boundary in bytes | `[64,512]` |
| SmallGroup | First `N/2` data headers | - |
| LargeGroup | Remaining data headers | - |

The client handshake obfuscation head is always 32 bytes on the wire. Its leading magic has effective length `3..8`; the rest of the 32-byte head carries a server-key-derived version field and 0..3 shuffled fields, then random filler. It is followed by an 8-byte header auth tag. Later data headers are always 6 bytes on the wire. Their checked magic span and optional plaintext fields are key-derived from the first-head layout: if `len` or `packet ID` appears in the first-head shuffle fields, the same field also appears in later headers, preserving the first-head order between those fields.

`header_type` controls the generated `Head` byte range:

- `"printable"`: `Head` bytes are visible ASCII, `0x21..0x7e`.
- `"any"`: `Head` bytes may be any byte, `0x00..0xff`.
- `"ALPHABET"`: `Head` bytes are uppercase English letters, `A-Z`.
- `"Alphabet"`: the first `Head` byte is an uppercase English letter, `A-Z`; remaining `Head` bytes are lowercase English letters, `a-z`.
- `"alphabet"`: `Head` bytes are lowercase English letters, `a-z`.
- `"alnum"`: `Head` bytes are ASCII letters or digits, `A-Z`, `a-z`, or `0-9`.

### Exact PCG32 Generation Order: Server-Key Layout

The 32-byte client first-head layout is generated only from the global server `key`; it does not consume epoch-pool PCG output. Initialize PCG32 with `SHA256(key)`:

- seed: first 8 bytes, big-endian uint64
- sequence: next 8 bytes, big-endian uint64
- multiplier `6364136223846793005`
- increment `(sequence << 1) | 1`
- seeding steps: set `state=0`, call `next()`, add seed to `state`, then call `next()` again.

Then consume PCG32 in this exact order:

1. Generate `MagicLen = next() % (HandshakeObfMagicMaxLen - HandshakeObfHeaderMinLen + 1) + HandshakeObfHeaderMinLen`, producing `3..8`.
2. Generate `VersionKind = next() % 4`, selecting one of: no version, 4-byte version, 6-byte version, or string version.
3. Generate three decimal version segment widths:
   - each width is `next() % 2 + 1`, producing `1..2`.
4. If `VersionKind` is string, generate `VersionLen = next() % 4 + 5`, producing `5..8`; otherwise the version length is fixed by the kind: `0`, `4`, or `6`.
5. Build the candidate shuffle field list in this order:
   - `len`, `fix ID`, `epoch ID`, `client ID`, `inc ID`, `packet ID`, `UTC`, `ID 1`, `ID 2`.
6. Shuffle all candidate fields with PCG32. For index `i`, choose `j ∈ [i, len-1]` from PCG32 and swap `array[i]` with `array[j]`.
7. Generate `ShuffleCount = next() % 4`, producing `0..3`, and use the first `ShuffleCount` fields from the shuffled list.
8. Initialize the selected fields in their shuffled order:
   - `len`: fixed size `2B`; generate `C = next() % 64`, producing `0..63`.
   - `fix ID`: choose size uniformly from `{1B,2B,4B}`, then generate a log-uniform constant for that unsigned width.
   - `epoch ID`: choose size uniformly from `{2B,4B}`.
   - `client ID`: choose size uniformly from `{2B,4B}`.
   - `inc ID`: fixed size `2B`; the client increments it once when creating a new mux connection for that server config.
   - `packet ID`: fixed size `2B`; the sender starts at `0`, increments once for each real mux packet sent and each fake header inserted into plaintext padding, and lets `uint16` wrap naturally.
   - `UTC`: fixed size `4B`.
   - `ID 1` / `ID 2`: choose size uniformly from `{1B,2B,4B}`, then generate a log-uniform constant for that unsigned width.
9. Generate the later-packet header layout:
   - Build `DataFields` from the selected first-head fields, preserving only `len` and `packet ID` in their first-head order.
   - Let `l = len(DataFields) * 2`. If `l == 0`, generate `DataMagicLen = next() % 5 + 2`, producing `2..6`. Otherwise generate the magic length in `2..min(4, 6-l)`; when both fields exist, `l == 4` and the only possible magic length is `2`.

The log-uniform constants use `f(10, maxUnsigned + 10) - 10`, where `f(a,b) = floor(exp(u * (ln(b) - ln(a)) + ln(a)))`, `u ∈ [0,1)`, and the result is clamped to the target unsigned width.

### Exact PCG32 Generation Order: Epoch Pool

Header pools are sensitive to the exact PRNG consumption order. Both client and server must generate the pool in this sequence:

1. Initialize PCG32 with seed `v`:
   - multiplier `6364136223846793005`
   - sequence `0xda3e39cb94b95bdb`
   - increment `(sequence << 1) | 1`
   - seeding steps: set `state=0`, call `next()`, add seed `v` to `state`, then call `next()` again.
2. Generate the handshake magic bytes:
   - Generate exactly `HandshakeObfMagicMaxLen` deterministic magic bytes.
3. Generate the handshake length offset:
   - `HandshakeLenOffset = next() % 65`, producing `0..64`.
4. Generate pool metadata:
   - `N = next() % 64 + 16`, producing `16..79`.
   - `Threshold = next() % 449 + 64`, producing `64..512`.
5. Generate `N` data headers in order:
   - For each header, choose `HeadLen = next() % (DataMagicLen - DataObfHeaderMinLen + 1) + DataObfHeaderMinLen`, producing `2..DataMagicLen`.
   - Generate exactly `HeadLen` deterministic head bytes.
   - Store the data-header magic span as `DataMagicLen` bytes: the generated bytes first, then zero bytes until `DataMagicLen`.
   - Generate that header's `DataLenOffset = next() % 18`, producing `0..17`.
   - If the checked magic span already exists in the pool, discard this header and repeat the whole per-header generation step until a unique checked magic span is produced.
   - The pool then builds a checked-magic-to-offset map from the unique data headers; both sender and receiver use this map.
6. Split the generated data headers without reshuffling:
   - `SmallGroup = headers[0 : N/2]`
   - `LargeGroup = headers[N/2 : N]`
7. Build deterministic padding thresholds:
   - Create an integer array containing every value from `MinPacketSize` to `MaxPacketPayloadSize - MaxDataPaddingSize`.
   - Shuffle the first `255` positions with PCG32. For index `i`, choose `j ∈ [i, len-1]` from PCG32 and swap `array[i]` with `array[j]`.
   - Sort those first `255` selected values.
   - Build `PaddingThreshold[256]`: index `0` is `0`, indexes `1..255` are the sorted selected values.
8. Build deterministic padding sizes:
   - Build `PaddingSize[2][256]` from PCG32, row `0` first and row `1` second.
   - Define `f(a,b) = floor(exp(u * (ln(b) - ln(a)) + ln(a)))`, where `u` is drawn in `[0,1)` and `a >= 1`, producing values in `[a,b)`.
   - Each value is log-uniformly distributed in `0..MaxDataPaddingSize` by computing `f(10, MaxDataPaddingSize + 11) - 10`.
9. Build `PaddingRowLimit[256]` from PCG32; each value is `next() % 128`, producing `0..127`.
10. Generate `MinPadding = MinPaddingMin + byte(next())`, producing `16..271`.
11. Generate `MaxPadding = next() % 4096 + 4096`, producing `4096..8191`.

Deterministic head bytes are generated one byte at a time:

```text
for i = 0; i < Len; i++:
    x = next()
    if header_type == "any":
        Head[i] = x & 0xff
    else if header_type == "ALPHABET":
        Head[i] = x % 26 + 'A'
    else if header_type == "Alphabet":
        if i == 0:
            Head[i] = x % 26 + 'A'
        else:
            Head[i] = x % 26 + 'a'
    else if header_type == "alphabet":
        Head[i] = x % 26 + 'a'
    else if header_type == "alnum":
        Head[i] = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789"[x % 62]
    else:
        Head[i] = x % 0x5e + 0x21
```

For example, when `hsLen = 5`, the handshake `Head` consumes five consecutive PCG32 outputs: `Head[0] = f(next #1)`, `Head[1] = f(next #2)`, ..., `Head[4] = f(next #5)`.

The random trailing bytes that pad a header to its wire length are generated with `crypto/rand` when sending. They do not consume PCG32 output and are not checked during validation. For later-packet data magic, zero bytes that fill the deterministic magic span are part of the checked magic, not random filler.

### Client First-Head Layout

The client first packet starts with a 32-byte plaintext obfuscation head, followed by an 8-byte header auth tag, the 24-byte client nonce, the encrypted timestamp mux packet, and the encrypted data mux packet.

The 32-byte head is laid out in the server-key order described above: magic first, then the optional version field, then the selected shuffled fields, then random filler. The magic bytes come from the epoch pool; the effective magic length and all later field lengths/order come from the server-key layout. All integers are big-endian.

Field values are:

| Field | Size |
|:---|:---:|
| `len` | 2B, timestamp-packet padding length plus key-derived `C` for small padding; for `512 < padding <= 1500`, a random byte below `0xc0` makes it use a fake split in `[256, padding/2]` plus `C`; for padding above `1500`, it uses a fake split in `[256,1280)` plus `C`. `C ∈ [0,64)` |
| `fix ID` | 1B, 2B, or 4B, key-derived log-uniform constant |
| `epoch ID` | 2B or 4B, low bytes of raw ordered `epoch` |
| `client ID` | 2B or 4B, runtime random value generated per configured server |
| `inc ID` | 2B, runtime counter generated per configured server and incremented for each new mux connection |
| `UTC` | 4B, current UTC seconds |
| `ID 1` / `ID 2` | 1B, 2B, or 4B, random log-uniform values |

The first-packet header auth tag is:

```text
HMAC-SHA256(uint64be(v), handshakeHead32B)[:8]
```

### Later 6B Header Layout

Later packet plaintext obfuscation headers are always 6 bytes on the wire. Their layout is derived from the same server-key layout that defines the client first head:

```text
if the first-head layout selected len and/or packet ID:
    [DataMagicLen bytes checked magic, HeadLen bytes generated and the rest zero-filled]
    [selected 2B fields in first-head order: len and/or packet ID]
    [random filler until 6B]
else:
    [DataMagicLen bytes checked magic, HeadLen bytes generated and the rest zero-filled]
    [random filler until 6B]
```

`DataMagicLen` is key-derived. It is `2..6` with no optional fields, `2..4` with one optional field, and exactly `2` when both `len` and `packet ID` are present. Each pool entry still samples its generated `HeadLen` from `2..DataMagicLen`; bytes between `HeadLen` and `DataMagicLen` are deterministic zero bytes. For the later-header `len`, packets write `next_header_distance - DataLenOffset`, using the offset attached to the selected data magic header. `next_header_distance` is measured from the current obfuscation header to the next obfuscation header: the first fake header inside plaintext padding when present, otherwise the next real packet header after the packet MAC. For `packet ID`, each sender starts at `0`, writes the current 2-byte value, increments once per real mux packet and per fake header inserted into plaintext padding, and wraps at `uint16`.

### Sender Selection

- **Handshake packet**: uses `SelectHandshakeHeader`; first `Len` magic bytes are deterministic, the rest of the 32-byte head is filled by the server-key layout and random filler, and the following 8 bytes authenticate that head with `v`. If the first-head layout includes `len`, the timestamp packet writes `next_header_distance - HandshakeLenOffset + C`, where `C` is the first-head `len` constant generated by the server-key layout. The client first packet always includes the nonce in this distance.
- **Data packets**: use `SelectHeader`; a sigmoid chooses between `SmallGroup` and `LargeGroup`, then a power-law CDF samples within that group. If the key-derived later layout has a length field, the sender writes `next_header_distance - DataLenOffset` for the selected magic header.
  - `pLarge = 1 / (1 + exp(-(payloadSize - threshold) / (threshold × 0.2)))`
  - `SmallGroup` weight alpha is `0.7`; `LargeGroup` weight alpha is `1.5`.

### Receiver Validation

**Server before pool recovery:**

- `FindPoolForHandshake` verifies the 8-byte header auth tag by trying the current raw epoch and adjacent raw epochs, each transformed into `v`.
- The matching `v` is then used to generate and validate the pool.
- If a pool matches, it is installed for the connection.
- If no pool matches, the connection enters invalid drain mode.

**Later packets:**

- `ValidateHeader` checks `SmallGroup ∪ LargeGroup`.
- If the later layout has `len`, the receiver uses the matched magic header to recover `DataLenOffset` and checks that the declared next-header boundary is either the next real packet or a valid location inside authenticated plaintext padding. In debug mode it additionally follows the complete fake-header chain and requires the final boundary to reach the next real packet header exactly.
- For the client first timestamp packet, the first-head `len` stores `next_header_distance - HandshakeLenOffset + C`. The server subtracts `C` and recovers the declared boundary from the selected handshake magic offset; debug mode additionally validates the complete fake-header chain.
- Failure enters invalid drain mode.

## Mux Packet Format

Each transmitted mux packet has a plaintext obfuscation prefix, encrypted mux header/payload, plaintext padding, and plaintext packet MAC:

| Packet kind | Plaintext prefix | Encrypted content | Plaintext suffix |
|:---:|:---|:---|:---|
| Client first packet to server | `32B obfuscation head + 8B header auth` | `24B client nonce + timestamp header/payload` | `timestamp padding + packet MAC`, then the first channel-request packet follows |
| Server first packet to client | `6B obfuscation header` | `mux header/payload` | `padding + packet MAC` |
| Later packet | `6B obfuscation header` | `mux header/payload` | `padding + packet MAC` |

Each mux packet has this logical format:

| Field | Channel ID | Payload Length | Header Tail | Payload | Padding | Packet MAC |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| Length | 1 byte | 2 bytes | 3 bytes | N bytes | M bytes | 4 bytes |
| Meaning | Channel | Payload bytes | Header check or padding size + check | Data | Random padding | Packet check |
| Encryption | encrypted | encrypted | encrypted | encrypted | plaintext | plaintext |

### Fields

- **Channel ID**: channel identifier. `0` is keep-alive/control, `1` is timestamp validation, `2` is flow control, `3` is channel request, `4` is reverse route, `5..7` are reserved, and `8..255` are data channels.
- **Payload Length**: payload length, excluding padding.
- **Header Tail**: fixed 3-byte field. For ordinary non-empty data packets it is a 3-byte Header MAC. For special channels (`channel_id < 8`) and empty payload packets, the first 2 bytes are `Padding Size` and the final byte is a 1-byte Header MAC.
- **Header MAC**: HMAC-SHA256 truncated to 3 bytes for ordinary non-empty data packets, covering `[plaintext obf prefix + Channel ID + Payload Length]`. For special channels and empty payload packets, it is truncated to 1 byte and covers `[plaintext obf prefix + Channel ID + Payload Length + Padding Size]`.
- **Payload**: encrypted application data.
- **Padding**: plaintext random padding used for traffic obfuscation.
- **Packet MAC**: plaintext HMAC-SHA256 truncated to 4 bytes, covering `[plaintext obf prefix + encrypted mux header + encrypted payload + plaintext padding]`.

### Padding Policy

Data-packet padding uses the deterministic `PaddingThreshold` and `PaddingSize` arrays generated by the exact PCG32 order above.

For data channels, no padding is added when `payload length > MaxPacketPayloadSize - MaxDataPaddingSize`. Otherwise, the sender uses `lower_bound(PaddingThreshold, payload length)` to get index `i`, then chooses row `0` when `last payload byte <= PaddingRowLimit[i]`, or row `1` otherwise. The padding size is `PaddingSize[row][i]`.

Ordinary non-empty data packets do not store padding size explicitly; the receiver recomputes the padding size from the deterministic rule above and uses that value when reading the padding bytes. Because that rule depends on the plaintext payload, the receiver decrypts the payload bytes needed for padding-size calculation but does not deliver or process the payload until the packet MAC has passed. The server caches the current raw-epoch header pool and adjacent raw-epoch pools after converting each epoch to `v`. Any mismatch is detected by the packet MAC or by subsequent framing failure.

When plaintext padding is larger than `1500` bytes, its content is shaped to contain fake packet boundaries. The sender first chooses a split length in `[256,1280)`, fills that first section with random bytes, and then fills the remaining section with a fake 6-byte obfuscation header followed by random bytes that look like encrypted body data. If the fake header layout has `len`, its value points to the next fake header; the final fake header points across the remaining padding and packet MAC to the next real packet header. Large remaining sections are processed recursively with the same rule, so long plaintext padding can contain multiple fake headers.

The client first timestamp packet also uses fake padding for medium padding sizes: when `512 < padding <= 1500`, it draws one random byte, and if that byte is below `0xc0`, it chooses a split in `[256,padding/2]` and inserts a fake header after that split.

Special channels (`channel_id < 8`) and empty data-channel no-op packets store padding size in the first 2 bytes of Header Tail and do not use the table; their padding is random log-uniform in `MinPadding..MaxPadding` bytes by computing `f(MinPadding, MaxPadding + 1)`. `MinPadding` and `MaxPadding` are generated by the exact PCG32 order above.

When traffic is imbalanced, the connection may also send a probabilistic channel 0 keep-alive control packet (`[00][00]`) to add reply traffic:

- Each TCP/mux connection creates a random threshold `T ∈ [64,191]`.
- Each time `sent traffic × 3 < received traffic`, it generates `R ∈ [0,255]`.
- A balance reply is sent only when `R < T`.

### Special Channels

| Channel ID | Purpose | Description |
|:---:|:---:|:---|
| 0 | Keep-alive/control | Encrypted payload is exactly 2 bytes `[target][control]`; see Channel 0 Control below. |
| 1 | Timestamp validation | Anti-replay; must be sent first. |
| 2 | Flow control | Per-channel window update messages. |
| 3 | Channel request | Creates a data channel; payload is `[data_channel_id][proxy_level][connection request]`. |
| 4 | Reverse route | Route update fragments; payload is `[json_len:2B][more:1B][json_fragment]`. |
| 5-7 | Reserved | Reserved for future use. |
| 8-255 | Data | Application traffic. |

For channel `3`, direct clients send `proxy_level=0`. Each reverse-route hop increments it before forwarding the request. A server rejects the request and logs loop detection when `proxy_level >= 16`.

Channel `4` fragments reassemble into a JSON object with `accept`, `reject`, `ipv6_prefix96`, and optional unsigned integer `priority` fields. Missing `priority`, including updates sent by older versions, means `256`. Smaller priority values are matched first; within the same priority, newer registrations are matched before older registrations. Receivers that predate `priority` ignore the additional JSON field.

Channel `0` carries whole-mux keep-alive/auth controls and per-data-channel
setup/lifecycle controls. Its complete payload definition is in
[Channel 0 Control](#channel-0-control).

### Per-Channel Flow Control

Each data channel has an independent dynamic receive window in each direction. New channels start with `256 KiB` of send credit. The receive window has a `64 KiB` minimum, starts at `256 KiB`, doubles at each step, and caps at `128 MiB`.

After each received payload is enqueued, the receiver compares its mux queue size with the current window. Three consecutive samples at or above `window/2` grow the window by one step. The window also grows after three sustained-throughput samples where received payload bytes accumulate to at least one full current window, which helps high-throughput streams grow even when the application drains quickly. Sixteen consecutive samples below `window/8` shrink the window by one step only if the accumulated low-buffer payload bytes are still below `window/2`. Shrinking cannot move below the currently buffered data, and already advertised credit is gradually withheld from later `WINDOW_UPDATE` messages instead of being revoked with a negative update.

TCP relay reads and mux data writes are capped by `MaxPacketPayloadSize`; when credit reaches zero, only that channel waits.

`MaxPacketPayloadSize` is derived from the later-packet wire limit: `MaxPacketSize - DataObfHeaderSize - HeaderSize - PacketMACSize`. The TCP relay also reads at this payload limit so a full relay read does not split into one maximum mux packet plus a small fixed tail packet.

Flow control uses channel `2`. Its encrypted payload is:

| Field | Type | Channel ID | Credit |
|:---:|:---:|:---:|:---:|
| Length | 1 byte | 1 byte | 4 bytes |
| Meaning | Message type | Data channel | Released bytes |

- `Type = 1` means `WINDOW_UPDATE`.
- `Credit` is a big-endian uint32 delta, not an absolute window value.
- Credit is released after payload bytes leave the mux receive queue.
- `WINDOW_UPDATE` messages are batched with a per-channel random threshold in `[window/16, window/4]`; after each update is sent, a new threshold is generated from the current window.
- `NetConn` may keep the unread remainder of one mux packet in its local partial-read buffer; the flow-control boundary is the mux queue, not the final application read.
- If a received payload would exceed the channel's receive window, the mux connection enters invalid drain mode.

### Timestamp Validation

- Before the first real data packet, the client sends a channel 1 timestamp packet.
- Timestamp payload is `ClientID(8 bytes) + UTC millisecond timestamp(8 bytes)`.
- Timestamp `ClientID` is generated randomly per configured server and is shared by TCP and UDP muxes for that server. This is separate from the first-head `client ID` field, which remains per configured server during the client process lifetime.
- Receiver checks:
  - Local clock drift must be within 5 minutes.
  - Replay resistance is provided by the authenticated client nonce and server nonce cache; timestamp values are not required to be monotonic.
- Failure enters invalid drain mode.

### Keep-Alive

- When no packets are sent or received for the local randomized interval, that side sends a keep-alive packet. The interval is re-randomized in the range 16-79 seconds after each received or sent packet.
- Normal keep-alive uses channel ID `0` with payload `[00][00]`.
- `[00][00]` is one-way: receivers update packet activity, reset their local keep-alive timer with a new random interval, and do not automatically reply with another keep-alive. It does not refresh the 600-second no-real-data timer.
- Receivers accept channel ID `0` payload `[00][01]` to refresh the 600-second no-real-data idle timer. Reverse upstream muxes emit this refresh-idle mode before receiving their first channel request, then switch to normal keep-alive after channel traffic begins.
- A non-empty channel `3` request and any non-empty data-channel packet count as real data and refresh the 600-second timer. Other special-channel controls and empty data packets do not.
- The connection is closed after 120 seconds with no packets.
- The connection is closed after 600 seconds with no real data.

### Channel Allocation

- Channel IDs start at 8 and increase monotonically.
- Channel IDs are never reused.
- Each client mux can allocate 128 data channels by default, configurable up to 224.
- After the limit is reached, a new socket connection is required.
- Each client mux can keep 32 active data channels by default, configurable up to 224.
- A client mux stops accepting new channels after 600 seconds by default, configurable in `[60,3600]` seconds. Existing channels continue running.
- Concurrent requests waiting for a new TCP mux are grouped into batches of at most 16; excess waiters start another mux creation in parallel.
- A server-to-server reverse upstream mux has no ordinary client allocation-age limit and uses 224 as both its allocation and active-channel limit. The initiating server registers a replacement after 24 hours or once the allocation count exceeds 112. The previous mux continues refresh-idle keepalives until the replacement authenticates and sends its route update; it then stops refresh-idle keepalives and may drain existing channels until normal idle handling closes it.

### Client Server Selection

Servers are identified by `(server_addr host, server_addr port, key)`, so future config reloads can match the same server without relying on list indexes.

For TCP `CONNECT`, the client first tries to allocate from an existing healthy mux. It creates a new TCP mux only when no healthy existing mux can allocate a channel. An unhealthy existing mux is not reused, but it does not prevent the client from opening another mux.

Server health classes are ordered from worst to best as `NoResponse`, `BadResponse`, `DialFailed`, `Degraded`, and `Good`:

- `DialFailed`: TCP dial failed. Retry delays are `2s, 5s, 15s, 60s, 120s`.
- `NoResponse`: dial succeeded but no server channel response arrived before timeout. Retry delays are `30s, 60s, 120s, 300s, 600s`.
- `BadResponse`: the server replied with an invalid channel response, such as an empty TCP connect or UDP associate response. Retry delays are `10s, 25s, 75s, 300s, 600s`.
- `Degraded`: a previously usable server had transient channel timeout, mux write failure, write timeout, or an unexpected mux close while channels were active.
- `Good`: the server has no active penalty.

Health penalties decay every 5 minutes by multiplying the negative score by `0.7` and truncating to an integer, so old transient failures eventually stop dominating selection. Each server also tracks the last time for each error kind; repeated errors of the same kind within 2 seconds refresh that timestamp but do not add another penalty or retry-count increment. A server in any hard-failure cooldown is skipped while another server is ready. If every configured server is cooling down, one is selected randomly with weight `1 / ln(remaining_cooldown_seconds + 1)`, favoring shorter remaining cooldowns without pinning every retry to one server.

Passive speed is tracked per server, shared by all muxes for the same server identity. Traffic is grouped into UTC-second buckets; idle seconds with no traffic are not inserted. A bucket direction is valid when it has at least 8 packets or more than 32 KiB in that direction. Buckets older than 10 minutes are pruned, and at most 30 buckets are retained. Upload and download are scored separately: if fewer than 3 valid buckets exist, all valid buckets are averaged; otherwise the best consecutive 3-bucket average is used. The final speed is the larger of the upload and download scores. Servers without measured speed start with a default `1 MiB/s` score.

Each TCP connect or UDP associate records server RTT from sending its channel `3` request until receiving `[data_channel_id][0x04]`. The selected server sends this acknowledgement immediately after registering and parsing the request, before reverse-route forwarding or target setup, so those downstream costs are excluded. The client keeps the most recent 5 samples and uses their average. A server without RTT samples uses `100 ms`. The timestamp/auth OK control still confirms that the server has replied on the mux, but its handshake ping is not used for ranking. Among otherwise comparable servers, ranking uses:

```text
score = speed / ln(server_rtt_ms + 2)
```

### Client Mux Timeouts

TCP dialing to a server uses a 10-second timeout. SOCKS5 handshakes on the local client listener also use a 10-second deadline.

Mux writes set a 10-second write deadline on the raw TCP connection. A write timeout marks the server degraded and closes the affected mux. Other mux write errors also degrade the server.

For TCP connect and UDP associate requests, `server_response_timeout` is one overall deadline from sending the channel request through receiving the final target setup result. The intermediate channel-accepted acknowledgement does not extend it. If a mux sees more than 8 server-response timeouts, the client closes that mux and applies a server health penalty. A timeout before any server traffic is received is treated as `NoResponse`; a timeout on a server that has previously exchanged traffic is treated as a transient degraded state.

## Channel Protocol

Data channels carry forwarded bytes only. Channel creation is requested through special channel `3`; setup results and lifecycle controls use special channel `0`. An empty data-channel payload is a valid no-op.

### Client Connection Request

The client sends a special channel `3` packet before using a new data channel. Its encrypted payload is:

| Field | Data Channel ID | Proxy Level | Connection Request |
|:---:|:---:|:---:|:---:|
| Length | 1 byte | 1 byte | Variable |

The `Connection Request` field is:

| Field | Connection Type | Address Type | Address | Port |
|:---:|:---:|:---:|:---:|:---:|
| Length | 1 byte | 1 byte | Variable | 2 bytes |

**Connection type**

| Value | Type | Description |
|:---:|:---:|:---|
| `0x01` | TCP | TCP connection over a shared mux connection. |
| `0x02` | UDP | UDP forwarding over a regular mux channel. |

**Address type**

| Value | Type | Address format |
|:---:|:---:|:---|
| `0x01` | IPv4 | 4-byte IP address |
| `0x03` | Domain | 1-byte length + domain string |
| `0x04` | IPv6 | 16-byte IP address |

Examples:

- TCP IPv4: `[01][01][C0 A8 01 01][00 50]` means TCP `192.168.1.1:80`.
- TCP domain: `[01][03][0B]example.com[01 BB]` means TCP `example.com:443`.
- UDP IPv4: `[02][01][08 08 08 08][00 35]` means UDP `8.8.8.8:53`.

### Channel 0 Control

Channel `0` has an encrypted payload of exactly 2 bytes: `[target][control]`. `target=0x00` controls the whole mux, while `target>=0x08` controls that data channel. Targets `0x01..0x07`, payloads of any other length (including an empty payload), and control values not listed below are invalid.

Whole-mux controls (`target=0x00`):

| Payload | Meaning |
|:---:|:---|
| `[00][00]` | Normal keep-alive / probabilistic traffic-balance reply. It updates packet activity but does not refresh the 600-second no-real-data timer. |
| `[00][01]` | Refresh-idle keep-alive. It refreshes the no-real-data timer; reverse upstream muxes send it before their first channel request. |
| `[00][02]` | Timestamp/auth validation succeeded. The server sends it after accepting channel `1`, confirming that the client handshake decrypted correctly and that the server can reply on the mux. |

Per-data-channel controls (`target=data_channel_id`, `0x08..0xFF`):

| Control | Meaning |
|:---:|:---|
| `0x00` | Target connect/associate succeeded. |
| `0x01` | Target connect/associate failed. |
| `0x02` | FIN: the sender will transmit no more data; the reverse direction remains open. |
| `0x03` | CLOSE: abort both directions and release the channel immediately. |
| `0x04` | ACCEPTED: the receiving server registered and parsed the channel request; target setup is still pending. |

The receiving server sends `[data_channel_id][0x04]` before reverse-route forwarding or target setup. It later sends the separate final result `[data_channel_id][0x00]` or `[data_channel_id][0x01]`. FIN and CLOSE may be sent by either endpoint after channel creation. A well-formed control for a data-channel ID that is no longer registered is ignored, which makes late FIN/CLOSE/response packets harmless. An empty channel `0` payload is invalid; an empty data-channel payload remains a valid no-op.

### TCP Connect Cache

For TCP `CONNECT`, the client keeps a local success cache keyed by `(server_addr, server_port, key, target_addr)`. A successful server response stores the entry for 10 minutes; repeated access refreshes its lifetime. The cache holds up to 1024 entries and evicts the least recently used entry when full.

On a cache hit, the client sends the SOCKS5 success reply immediately after writing the channel `3` connect request, then still waits for the server's channel response in the background. If the server later reports failure or the response times out, the entry is removed and that local proxy request is closed.

### Data Forwarding

After the connection is established, all later packets transparently carry raw data.

### Half-Close and Abort

On a clean source EOF, the relay sends `[data_channel_id][0x02]` through special channel `0`. The receiver drains already queued data and then returns EOF for that direction, while retaining the ability to send in the reverse direction. When its own source also reaches EOF, it sends its own FIN. After both FINs, each side releases local channel state without sending CLOSE.

Read/write errors and explicit cancellation send `[data_channel_id][0x03]`, which aborts both directions and releases the channel immediately. Empty data-channel payloads are accepted as no-ops and carry no lifecycle meaning.

## UDP Forwarding

UDP traffic uses regular mux channels and implements Full Cone NAT behavior.

### Setup

1. **SOCKS5 handshake**
   - The local application sends `UDP ASSOCIATE` to the client proxy.
   - The client allocates a channel from the shared mux pool, using the same selection and health scoring as TCP channels.
   - The channel `3` request payload marks the data channel as UDP with `ConnType=0x02`.

2. **Local UDP listener**
   - The client creates a local UDP socket on `127.0.0.1:random_port`.
   - The client returns that UDP port through SOCKS5 `SendReply`.

3. **Server negotiation**
   - The client sends a channel `3` connection request with `ConnType=0x02` and the target address.
   - The server replies `0x04` after registering the channel, then creates a UDP socket and replies `0x00`.

### UDP Stream Framing

Each UDP data channel is a byte stream. Every datagram is length-prefixed so it
can be reconstructed after flow control or mux packet-size limits split it
across multiple mux packets. The 2-byte big-endian `Body Length` covers
`Address Type + Address + Port + Data` and excludes the length field itself.

**Client to server, inside mux channel**

| Field | Body Length | Address Type | Address | Port | Data |
|:---:|:---:|:---:|:---:|:---:|:---:|
| Length | 2 bytes | 1 byte | Variable | 2 bytes | Variable |

- The client parses the SOCKS5 UDP packet and extracts target address and data.
- It encodes them into the custom mux-channel format.

**Server to client, inside mux channel**

| Field | Body Length | Address Type | Source Address | Source Port | Data |
|:---:|:---:|:---:|:---:|:---:|:---:|
| Length | 2 bytes | 1 byte | Variable | 2 bytes | Variable |

- The server preserves the actual UDP source address and port in the mux frame.
- The client uses those fields when constructing the SOCKS5 UDP response for the local application.

### Full Cone NAT

The server implements Full Cone NAT behavior:

- **Single relay socket**: one unconnected UDP socket sends to requested targets and accepts responses from any source.
- **Any-source receive**: the UDP socket accepts packets from any source address.
- **Forward all**: every received UDP packet is sent back to the client without source filtering.
- **Preserve source**: every forwarded response retains the source address and port observed by the server socket.
- **Bidirectional traffic**: supports P2P hole punching and multi-source responses.

This allows UDP applications such as BitTorrent and video calls to work normally.

### Connection Management

- **Shared mux pool**: UDP and TCP channels are allocated from the same client mux pool.
- **Selection**: new UDP allocations use the same health, passive speed, and server RTT scoring as TCP channel allocation.
- **Cleanup**: a mux is closed when it is idle, closed by the peer, or no longer allocatable and has no active channels.
- **TCP control**: the SOCKS5 TCP control connection is monitored; if it closes, UDP forwarding stops.
- **End signal**: UDP association shutdown uses channel `0` CLOSE; an empty data payload is a no-op.
- **Cleanup**: all resources are released when the connection closes.

## Invalid Drain Mode

When a connection enters invalid state before timestamp authentication, the server continues reading and discarding data until a timeout closes the connection. The timeout is derived from `key` and is in the range 8-39 seconds. The close deadline is fixed at socket creation time as `created_at + timeout`; entering invalid state later only waits until that existing deadline. The server also closes the socket if the timestamp packet has not authenticated before the same deadline. After timestamp authentication and after that fixed deadline has passed, a later authentication failure enters a second drain stage with a random 10-60 second timeout.

Current invalid-state causes include:

1. Obfuscation header validation failure, including failed server-side pool recovery.
2. MAC validation failure.
3. Timestamp validation failure.
4. User nonce authentication failure.
5. Missing timestamp before data.
6. Bad channel request format.
7. Channel ID outside the valid data-channel range.
8. Per-channel flow-control window violation.

## Secret Strength Warnings

The server prints a warning when the global `key` or any configured user `password` is weak. A value is considered weak when it is shorter than 14 characters, or when it is missing any one of uppercase letters, lowercase letters, or digits. User password warnings include the user name.

## MAC

Packets use HMAC-SHA256 with an independent salt. The mux MAC key is derived from the per-epoch user secret:

```go
macKey := PBKDF2-HMAC-SHA256(userSecret, "mux-mac:", 32, 32)
```

- Header MAC is truncated to 3 bytes for ordinary non-empty data packets, and to 1 byte for special channels or empty payload packets.
- Packet MAC is truncated to 4 bytes.
- MAC validation failure enters invalid drain mode.

## Limits

- Default channel allocations per socket: 128; configurable client muxes and reverse upstream muxes can use up to 224.
- Default concurrent channels per socket: 32; reverse upstream muxes use 224 so they have no smaller separate active-channel cap.
- Maximum later packet wire size: 32768 bytes.
- Maximum later packet payload size: 32752 bytes.
- Socket idle timeout: 120 seconds with no packets.
- No-real-data timeout: 600 seconds.
